# Approval Finalizer architecture — design only (2026-09-27)

**Status: unimplemented; TRUST_ANCHOR_ISOLATION=NO.** This is the contract and existing-path inventory, not permission to create CT122, change ACLs, deploy a verifier, generate a key or execute Approver Stage 2. See `human-approver-security.md` for the signed-v1 wire format/key lifecycle; `pve-doc/docs/human-approver-ct-plan.md` owns PVE and human-admin operations.

## Authority and threat boundary

CT121 issues self-binding signed evidence after human UV; it does **not** own registry or DONE. An independently administered approval-finalizer (CT122 is a proposed instance) owns protected registry, verifier/runtime/dependencies/config/startup, replay and completion DB, audit and **authoritative DONE record**. Treat all AI-Workspace processes, local `workspace` identity, MCP/CLI/Dashboard inputs, `.ai/tasks/*/status.json`, Review pointer and local approval files as fully compromised. AI may submit evidence and query a bounded result; it cannot administer CT122, mutate its disks/backup/restore, change its service or impersonate a trusted Review publisher. A Finalizer record's absence means *not DONE* even if any local ledger, API or UI says `DONE`. AI's ledger/UI is only a projection; production downstream actions must query authenticated Finalizer state, not accept a locally cached response or a bare hash as authority. Existing read-only-job `DONE` means worker finished, not a human-approved change; give it a separate label/namespace so it cannot satisfy authoritative completion.

The chosen Review authority is **not yet available**. `CURRENT_REVIEW.json`, `rpc-jobs/authoritative/<task>.json`, review `result.json`, source `.ai` and published bundle are currently writable by the compromised principal. Re-hashing or fetching them from CT122 does not cure fabricated PASS or stale currentness. Before Phase B/D, introduce an independent Review-owned publisher and protected latest-generation register (separate identity/domain from AI, distinct from CT121; may be a tightly isolated component within CT122 if Review creation/semantic judgment and its credentials are also independent). It must validate independently produced semantic PASS, immutable exact review result raw-byte hash, manifest, canonical goal, task/run and integration/commit identity if required, and publish monotonically versioned per-task latest/invalidated Review facts under its own authenticated identity. AI may submit *candidate* bundles only; it cannot issue or replace PASS/currentness or roll back the register. Finalizer fetches the latest facts by task ID from this source, verifies identity, sequence and revocation/currentness at commit, and refuses when unavailable, contradictory or unable to validate the relevant source snapshot. Git/working-tree mutability and post-review changes need a protected immutable content/commit anchor plus independent currentness/commit attestation or a protected freeze gate; local `READY_FOR_REVIEW` and `CURRENT_REVIEW.json` alone are insufficient. Whether this independent Review source is feasible and who operates it is an explicit human decision, not an implementation claim.

## Finalization request, commit and result

Finalizer-owned registry records have `key_id` (globally unique; never reused), `algorithm` (v1 Ed25519), canonical SPKI `public_key`, SHA-256 SPKI `fingerprint`, `activated_at`, nullable `retired_at`/`revoked_at`, `status` exactly `ACTIVE`/`RETIRED`/`REVOKED`, and `reason`. Human-admin-only authenticated mutation increments an anti-rollback generation and preserves immutable prior versions and audit. Unknown status, conflicting ID/fingerprint, reversed timestamps, missing/rolled-back generation fail closed. Only ACTIVE permits LIVE; RETIRED allows historical signature checking only; REVOKED never authorizes LIVE. If a leaked key can backdate `issued_at`, even a valid historical signature does not independently prove pre-compromise issuance. Registry, code, dependency, service definition, replay/completion/audit storage must be outside AI-controlled credentials/ACLs, including parent paths and backup/restore rights; a filesystem readonly attribute is not isolation.

AI may relay CT121's strict v1 signed approval (request_id, task_id, run_id, authoritative_review_id, review_evidence_hash, bundle_manifest_sha256, canonical_goal_sha256, issued_at, expires_at, nonce/JTI, key ID, signature). The relay is untrusted: never infer approval from transport, caller-supplied `trustedContext`, a PASS boolean or a browser session. The Finalizer obtains authoritative Review/currentness and content binding itself, checks exact fields and request_id uniqueness where appropriate, signature, algorithm, registry ACTIVE *now*, activation/retirement/revocation boundaries, time/skew/expiry, and verifies that an authenticated independently issued Review PASS is still current. Require finalization target identity (repo/task/run, mode and integration target) in the independently trusted context; reject cross-repo collisions. CT121→Finalizer direct retrieval might reduce relay loss/exposure but adds network credentials/availability coupling and **does not** replace self-binding or independent Review confirmation; v1 recommendation is untrusted AI relay. Rate-limit submission without granting state-write rights.

Make expiry, registry state, Review generation and unused JTI true at the **commit linearization point**, not only at a preflight read. Use one Finalizer-owned transactional DB with unique `(issuer_domain, key_id, jti)`, unique `(issuer_domain, request_id)` for completed requests, and unique `(repo_id, task_id, run_id)` completion keys (plus unique approval evidence hash); all reads of mutable registry/current Review generation must be serialized with their writers, or use protected generation checks in the same transaction. A signed, immutable Review snapshot with version alone is insufficient if new reviews can supersede it without a coordinated register. Conceptual flow: validate candidate/cryptography and trusted Review; `BEGIN IMMEDIATE` (or equivalent serializable transaction); recheck clock/expiry, registry version/status, protected latest Review generation and exact bindings; reject existing JTI/request/task completion; insert consumed JTI; insert immutable completion record with registry/Review generations and hashes; append transactionally linked audit event; `COMMIT`. Any failed insertion/check rolls back **both** JTI and completion. Return a prior receipt *only after an authenticated read of the already committed identical record*; never consume a new JTI or create a second DONE on retry. On timeout/unknown commit, query by task/evidence hash; never fall back to legacy completion. Define crash-safe DB durability, backup/recovery and anti-rollback for registry, Review register, JTI, completion and audit **as one consistency domain** before deployment; a stale restored DB must not reauthorize consumed evidence.

Successful receipt fields: `schema_version`, `finalization_id` (unique opaque ID), `repo_id`, `task_id`, `run_id`, `approval_evidence_hash` (hash of canonical received signed evidence bytes), `request_id`, `key_id`, `authoritative_review_id`, `review_evidence_hash`, `bundle_manifest_sha256`, `canonical_goal_sha256`, `review_generation`, `registry_generation`, `completion_timestamp`, `finalization_record_hash` (hash of canonically encoded immutable record). The Finalizer serves the record over an authenticated pinned endpoint; a local AI copy of this receipt/hash is not sufficient proof. Exact canonical receipt encoding, issuer identity and domain separation must be specified/tested before code. Audit-only verification is a separate endpoint/mode: RETIRED evidence from its valid period may be cryptographically checked but never committed as new DONE; REVOKED/compromised evidence reports trusted independently anchored compromise cutoff or indeterminate trust if timing cannot be proved. Retain old keys and audit.

If CT121 or CT122 or Review authority is unavailable, key/registry/currentness conflicts arise, time is untrusted or transaction outcome is uncertain: **FAIL CLOSED**, show `READY_FOR_HUMAN_FINALIZATION` (or equivalent local waiting state), no legacy fallback. CT121 private key has no initial backup; loss suspends finalization, triggers new Approver trust domain/key/ID, human-only registry update and old-key retirement (revocation for compromise), Passkey re-enrollment and negative E2E before restart.

## Negative E2E matrix (future, independent principals)

| Input/attack | Expected |
| --- | --- |
| Unknown key; random signature; unknown registry status/rollback | Reject, zero completion/JTI writes. |
| RETIRED or REVOKED key for LIVE; pre-activation or post-retirement/revocation issued_at | Reject. RETIRED historical verification is audit-only; REVOKED report includes compromise-time confidence. |
| Expired evidence; future issued_at; duplicate request/JTI; concurrent double-submit; crash before/after commit | Reject or return authenticated *same* prior record after commit; never two records or lost JTI without DONE. |
| task/run/repo/request/review ID, raw Review hash, bundle manifest, goal hash, integrated commit mismatch; forged/stale PASS/currentness; mutable bundle after Review | Reject; no trust in AI-controlled pointer or PASS boolean. |
| AI token attempts registry/code/build/dependency/config/service/startup/restart/replay/completion/audit/Review-authority tamper, PVE config/status/power/console/snapshot/backup/storage/migrate/delete/exec/ACL | Denied by effective identity/network/PVE rights and independently checked unchanged protected state. |
| Direct engine `DONE`, `done_approved=true` alone, Dashboard route/fixture, MCP/CLI bypass, forged local receipt or local `.ai` DONE, Finalizer/Review/Approver outage | No authoritative DONE; protected record absent, downstream/UI cannot mistake projection for authorization. |

Phases: **A** architecture/source of truth and Review-authority decision; **B** Finalizer registry, service, replay/completion DB and independent Review publication contract; **C** isolated CT122 deployment after human-admin approval; **D** CT121 signed-evidence non-production E2E; **E** close every legacy completion writer/consumer; **F** controlled negative E2E and separately approved production activation. Each phase has its own threat review; phases are not permission to execute now.
