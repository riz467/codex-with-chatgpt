# AI-Workspace local orchestration gateway (Windows)

> For day-to-day use start with [Quick Start](ai-workspace-quickstart.md); for the active VM deployment and troubleshooting see [Runbook](ai-workspace-runbook.md); for design see [Architecture](ai-workspace-architecture.md). This page retains detailed adapter and cutover notes.

This deployment adds bounded orchestration and completion tools, approval/retry readers, and read-only repository research (`search_repo`, `read_repo_file`) to the original workspace tools. For the exact per-Bridge [tool catalog and scopes](ai-workspace-architecture.md#tool-catalog-and-permissions), use the Architecture page; `src/mcp/server.ts` is authoritative. The gateway is an adapter, **not** an orchestration engine: `ai-run.ps1` / `orchestrate-v03.ps1` own task transitions and review publication.

## Local operation

For isolated development only (not on the scheduled VM), build with `corepack pnpm build`, test with `corepack pnpm test`, and start the bridge with `node bin/c2c.js start --workspace C:\work\codex-with-chatgpt --json` (without `--tunnel` during local review). It binds to `127.0.0.1`; inspect the reported port, then GET `http://127.0.0.1:<port>/health`. POST `/mcp` requires a workspace-bound OAuth bearer token. A request without one returns 401. Use `tools/list` through an authorized MCP client to inspect the tool catalog. `c2c status -w C:\work\codex-with-chatgpt` shows bridge state. On the scheduled VM, use the [Runbook](ai-workspace-runbook.md) scripts instead of starting another Bridge.

**Final review connector:** `workspace_info` and `read_file` always use the Bridge's bound workspace, not the separate `REVIEW_ROOT` used by the integrity tool. On the scheduled VM deployment, use the existing review-bound Bridge at `127.0.0.1:54108` (do not start a second Bridge). For isolated local review only, start a review-bound Bridge with `node bin/c2c.js start -w C:\work\ai-orchestration-review --json`, check its distinct `workspaceId` and port, and authenticate an MCP client to **that** workspace before reading `CURRENT_REVIEW.json`. A tunnel routed to a Bridge bound to `C:\work\codex-with-chatgpt` will not serve review-workspace files even though `verify_bundle_integrity` reads the fixed review root. The VM's named Cloudflare tunnel currently has two hostname routes: `ai-workspace-mcp.m1n4m0.me` to `127.0.0.1:48765` (orchestration Bridge) and `ai-orchestration-review.m1n4m0.me` to `127.0.0.1:54108` (review Bridge). Check both local and public `/health` endpoints independently; a local Bridge restart can change its port and make a route stale. Routing and OAuth consent are operational configuration, not enforced by this repository. A review hostname or `workspace_info.readOnly` does **not** restrict the whole Bridge: `orchestration.start` still authorizes `start_test_job`, `start_orchestration` and `retry_orchestration` there. Only the two completion write tools are not registered on the review-bound Bridge.

Scopes: `review.read` for integrity, repository research, status/result, approval inspection and retry planning; `orchestration.start` for the bounded start/retry actions and, only on the execution-bound Bridge, completion. Existing OAuth grants do not automatically gain new scopes: reauthorize the ChatGPT app and review the consent page before using actions. Do not add these scopes to unrelated clients.

1. Call `start_test_job` first (no arguments). It creates only `C:\work\ai-orchestration-review\rpc-test\<request_id>.json` with `request_id`, `timestamp`, `marker`, `source`. Confirm the marker locally before enabling production work.
2. `verify_bundle_integrity` takes no argument for `CURRENT_REVIEW.json`, or `bundle: "reviews/<published-name>"`. It compares raw-byte SHA-256 of `manifest.json` to `review-bundle.json` and each payload to the manifest. It never modifies evidence. Missing, mismatch, extra and invalid entries are returned as small issue records.
3. When authorized, `start_orchestration` requires `repo` (`pve-doc` or `ai-orchestration-config`), `mode` (`read_only` or `change`), and a bounded `goal`. `change` without `edit_paths` retains the original `ai-run.ps1` flow: scope discovery and every existing approval/verification gate. With `edit_paths` (1–5 existing repo-relative files), the fixed PowerShell adapter decodes a base64 JSON array into `[string[]]` and calls the same `ai-run.ps1 -EditPaths` parameter; PowerShell's native `-File` invocation does not bind multiple array values correctly when they are supplied as separate process arguments. The adapter rejects traversal, reparse points, globs, directories, sensitive files and paths outside the allowlisted repo; the engine still owns change authorization, verification and publication. `read_only` forbids `edit_paths` and never invokes ai-run: it runs the fixed Node inspection worker with an allowlisted repo key and generated IDs. The worker performs only fixed Git status/HEAD/branch checks and a root-directory count, writing a concise result to the job directory. The goal is **not interpreted as a command or a request to inspect arbitrary files**; for detailed investigation use the existing read-only workspace MCP tools. No shell string is evaluated in either mode. Start returns without waiting; one active RPC job per repo is refused, with no scheduler.
4. Poll `get_orchestration_status` with `{ "id": "<job-id-or-task-id>" }`, then `get_orchestration_result` with the same id. Each accepts exactly one of `id`, `job_id` or `task_id`; `task_id` reads fixed allowlisted engine ledgers even when the job registry is absent, including DONE tasks. Both responses include `mode`. The process status is adapter bookkeeping. In `change`, orchestration state comes **only** from `<repo>/.ai/tasks/<task-id>/status.json`; no independent change state is synthesized. A verified current review bundle is exposed for active registered review tasks; completed task lookup can also validate its recorded published bundle and review decision. In `read_only`, the fixed `read-only-result.json` under the job directory is the completion evidence; successful results have `state: DONE`, no changed paths or bundle, and `published: false`. Results and messages are capped; stdout/stderr are never returned. If a process ends before creating evidence, state remains null and the local operator must inspect the saved output.

An explicit edit scope bypasses **only** ai-run's edit-path discovery. The current engine masks complete, explicitly negated commit/push clauses (such as `commit・pushは禁止`) for goal-intent detection, but still gates positive requests, proposed commands and other risky operations. If the engine returns `NEEDS_APPROVAL`, do not automatically rephrase or retry the task to evade the gate; obtain a human decision through the normal workflow.

Adapter bookkeeping lives in `C:\work\ai-orchestration-review\rpc-jobs\<job-id>\` (`job.json`, `stdout.log`, `stderr.log`). The task ledger is in the allowlisted repo and is owned by ai-run. These directories must be accessible only to the trusted VM account. The adapter does not expose a generic shell, write, repo-path, environment, git-push, secret, or process-kill tool. Do not expose its locally issued admin token.

## Cloudflare / ChatGPT operation

The existing named Cloudflare tunnel forwards the two hostnames above to separate **loopback** Bridges. The public MCP URL for each is `https://<hostname>/mcp`; OAuth discovery and pairing endpoints must also be reachable on the same host. Confirm `/health` and an unauthorized `/mcp` returns 401 for each route, then verify each ChatGPT connector is bound to the intended workspace and has the intended OAuth scopes. Reconnect/re-authorize to obtain new scopes; review the consent text before calling `start_test_job`. Cloudflare DNS/tunnel changes and ChatGPT app changes require separate operator approval. This code does not configure Cloudflare DNS, tunnel ingress or ChatGPT connectors.

The README's V1 read-only security description applies to the original tools. This deployment adds bounded start/retry actions and engine-mediated completion on the execution-bound Bridge only. Treat enabling `orchestration.start` on either public tunnel as a deliberate security decision.

## Windows Server reboot operation

The gateway's two Bridges use the **workspace user's** `C:\Users\workspace\AppData\Local\codex-with-chatgpt\auth\<workspace-id>.json` OAuth registrations/token hashes and runtime state. The review and execution stores are separate. The pairing session is in memory, not durable. The named tunnel continues using `C:\Users\workspace\.cloudflared\config.yml` and its existing credentials file. Do not move these to LocalSystem or run `unpair` during cutover. Node is pinned to the workspace user's NVM install (`v24.16.0`); after changing NVM versions, update both the installer action and supervisor paths deliberately. The Bridge is launched as `serve`, **not** `start`, so it remains supervised and uses fixed ports rather than spawning its own detached process.

The deployment scripts register one Task Scheduler **AtStartup** task, `AI-Workspace-Gateway`, running as `workspace` via S4U (no password in a script or task). Register it from an **elevated PowerShell as workspace** using `scripts/install-ai-workspace-gateway.ps1` only when it is not already registered. A non-elevated session cannot register an AtStartup task (access denied); do not switch the foreground processes before registration succeeds. S4U has no network credentials: verify Cloudflare outbound connection and workspace profile access under the actual task identity. No interactive PowerShell or user logon is required once registration and validation succeed.

The task runs the fixed Node supervisor `scripts/run-ai-workspace-gateway.mjs`. It starts (and retries after exit) the following commands, with a preflight port/tunnel check to avoid known duplicates:

```
"C:\Users\workspace\AppData\Local\Author Software\nvm\installs\v24.16.0\node.exe" C:\work\codex-with-chatgpt\dist\cli\index.js serve --workspace C:\work\codex-with-chatgpt --port 48765
"C:\Users\workspace\AppData\Local\Author Software\nvm\installs\v24.16.0\node.exe" C:\work\codex-with-chatgpt\dist\cli\index.js serve --workspace C:\work\ai-orchestration-review --port 54108
"C:\Program Files (x86)\cloudflared\cloudflared.exe" --config C:\Users\workspace\.cloudflared\config.yml tunnel run ai-workspace-mcp
```

Output from children is intentionally discarded to prevent credentials, pairing codes or auth headers from entering logs. The supervisor writes only its own bounded PID/exit events to `C:\work\ai-workspace-logs\execution-bridge.log`, `review-bridge.log`, `cloudflared.log` (5 MiB per active file, three rotated files). Task Scheduler records task start failures and last result. Bridges may still use their own user-profile application logs: protect the workspace account and state directory. Cloudflared reconnects while a Bridge is warming up; `/health` on each public route is the readiness check. Note that the underlying Bridge can fall back to an ephemeral port on a *race* after the port preflight: always check both fixed listeners and health after cutover.

Cutover checklist (run locally, not in ChatGPT):

1. From an elevated `workspace` shell run `pwsh -NoProfile -File scripts/install-ai-workspace-gateway.ps1`; confirm Task Scheduler shows `AtStartup`, S4U and the expected action. Registration alone does not alter foreground processes.
2. Record baseline `pwsh -NoProfile -File scripts/status-ai-workspace-gateway.ps1` and the two workspace IDs in `/health`. Stop **only the three previously identified foreground PIDs** after confirming their command lines; the Bridge CLI `stop --workspace <path>` uses the private runtime admin token to shut down gracefully. Do not revoke OAuth tokens or delete the auth store. Stop the foreground cloudflared by its verified PID. Do not close unrelated PowerShell windows.
3. Run `pwsh -NoProfile -File scripts/start-ai-workspace-gateway.ps1`, then `pwsh -NoProfile -File scripts/status-ai-workspace-gateway.ps1`. Require task `Running`, the supervisor and three child processes, expected listener PIDs on 48765 and 54108, both local and public `/health` = 200 with the **same workspace IDs as baseline**, and anonymous `/mcp` = 401 on both public routes. Check last task result and bounded logs. A 200/401 response alone does not prove existing ChatGPT OAuth grants: verify both existing ChatGPT connectors can still authenticate and reach their intended workspaces with the correct scopes. If this fails, inspect account/profile and return to the known foreground setup without deleting any auth files.
4. For normal manual operation use `scripts/start-ai-workspace-gateway.ps1`, `scripts/status-ai-workspace-gateway.ps1`, and `scripts/stop-ai-workspace-gateway.ps1`. `stop` requires a running gateway task and only targets its fixed commands. Stopping does not disable the AtStartup trigger. Test a VM reboot **only after explicit human confirmation**, then repeat step 3 without an interactive logon. Do not assume that a manually started S4U task guarantees boot-time success.
