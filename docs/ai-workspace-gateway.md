# AI-Workspace local orchestration gateway (Windows)

This deployment adds five bounded MCP tools to the existing C2C Bridge. The original nine workspace tools remain read-only. The gateway is an adapter, **not** an orchestration engine: `ai-run.ps1` / `orchestrate-v03.ps1` own task transitions and review publication.

## Local operation

Build with `corepack pnpm build`, test with `corepack pnpm test`, and start the bridge with `node bin/c2c.js start --workspace C:\work\codex-with-chatgpt --json` (without `--tunnel` during local review). It binds to `127.0.0.1`; inspect the reported port, then GET `http://127.0.0.1:<port>/health`. POST `/mcp` requires a workspace-bound OAuth bearer token. A request without one returns 401. Use `tools/list` through an authorized MCP client to inspect the tool catalog. `c2c status -w C:\work\codex-with-chatgpt` shows bridge state.

**Final review connector:** `workspace_info` and `read_file` always use the Bridge's bound workspace, not the separate `REVIEW_ROOT` used by the integrity tool. Start a review-bound Bridge with `node bin/c2c.js start -w C:\work\ai-orchestration-review --json`, check its distinct `workspaceId` and port, and authenticate an MCP client to **that** workspace before reading `CURRENT_REVIEW.json`. A tunnel routed to a Bridge bound to `C:\work\codex-with-chatgpt` will not serve review-workspace files even though `verify_bundle_integrity` reads the fixed review root. The VM's named Cloudflare tunnel currently has two hostname routes: `ai-workspace-mcp.m1n4m0.me` to `127.0.0.1:48765` (orchestration Bridge) and `ai-orchestration-review.m1n4m0.me` to `127.0.0.1:54108` (review Bridge). Check both local and public `/health` endpoints independently; a local Bridge restart can change its port and make a route stale. Routing and OAuth consent are operational configuration, not enforced by this repository. Do not assume a review hostname or a `workspace_info.readOnly` field restricts the **whole** Bridge: that field describes workspace inspection tools, while the separate `orchestration.start` scope still grants the two bounded actions on either Bridge.

New scopes: `review.read` for integrity/status/result; `orchestration.start` for the two action tools. Existing OAuth grants do not automatically gain them: reauthorize the ChatGPT app and review the consent page before using actions. Do not add these scopes to unrelated clients.

1. Call `start_test_job` first (no arguments). It creates only `C:\work\ai-orchestration-review\rpc-test\<request_id>.json` with `request_id`, `timestamp`, `marker`, `source`. Confirm the marker locally before enabling production work.
2. `verify_bundle_integrity` takes no argument for `CURRENT_REVIEW.json`, or `bundle: "reviews/<published-name>"`. It compares raw-byte SHA-256 of `manifest.json` to `review-bundle.json` and each payload to the manifest. It never modifies evidence. Missing, mismatch, extra and invalid entries are returned as small issue records.
3. When authorized, `start_orchestration` requires `repo` (`pve-doc` or `ai-orchestration-config`), `mode` (`read_only` or `change`), and a bounded `goal`. `change` without `edit_paths` retains the original `ai-run.ps1` flow: scope discovery and every existing approval/verification gate. With `edit_paths` (1–5 existing repo-relative files), the fixed PowerShell adapter decodes a base64 JSON array into `[string[]]` and calls the same `ai-run.ps1 -EditPaths` parameter; PowerShell's native `-File` invocation does not bind multiple array values correctly when they are supplied as separate process arguments. The adapter rejects traversal, reparse points, globs, directories, sensitive files and paths outside the allowlisted repo; the engine still owns change authorization, verification and publication. `read_only` forbids `edit_paths` and never invokes ai-run: it runs the fixed Node inspection worker with an allowlisted repo key and generated IDs. The worker performs only fixed Git status/HEAD/branch checks and a root-directory count, writing a concise result to the job directory. The goal is **not interpreted as a command or a request to inspect arbitrary files**; for detailed investigation use the existing read-only workspace MCP tools. No shell string is evaluated in either mode. Start returns without waiting; one active RPC job per repo is refused, with no scheduler.
4. Poll `get_orchestration_status` with `{ "id": "<job-id-or-task-id>" }`, then `get_orchestration_result` with the same id. Both responses include `mode`. The process status is adapter bookkeeping. In `change`, orchestration state comes **only** from `<repo>/.ai/tasks/<task-id>/status.json`; no independent change state or bundle is synthesized. A published bundle is exposed only when `CURRENT_REVIEW.json` matches that task and verifies cleanly. In `read_only`, the fixed `read-only-result.json` under the job directory is the completion evidence; successful results have `state: DONE`, no changed paths or bundle, and `published: false`. Results and messages are capped; stdout/stderr are never returned. If a process ends before creating evidence, state remains null and the local operator must inspect the saved output.

An explicit edit scope bypasses **only** ai-run's edit-path discovery. The current engine masks complete, explicitly negated commit/push clauses (such as `commit・pushは禁止`) for goal-intent detection, but still gates positive requests, proposed commands and other risky operations. If the engine returns `NEEDS_APPROVAL`, do not automatically rephrase or retry the task to evade the gate; obtain a human decision through the normal workflow.

Adapter bookkeeping lives in `C:\work\ai-orchestration-review\rpc-jobs\<job-id>\` (`job.json`, `stdout.log`, `stderr.log`). The task ledger is in the allowlisted repo and is owned by ai-run. These directories must be accessible only to the trusted VM account. The adapter does not expose a generic shell, write, repo-path, environment, git-push, secret, or process-kill tool. Do not expose its locally issued admin token.

## Cloudflare / ChatGPT operation

The existing named Cloudflare tunnel forwards the two hostnames above to separate **loopback** Bridges. The public MCP URL for each is `https://<hostname>/mcp`; OAuth discovery and pairing endpoints must also be reachable on the same host. Confirm `/health` and an unauthorized `/mcp` returns 401 for each route, then verify each ChatGPT connector is bound to the intended workspace and has the intended OAuth scopes. Reconnect/re-authorize to obtain new scopes; review the consent text before calling `start_test_job`. Cloudflare DNS/tunnel changes and ChatGPT app changes require separate operator approval. This code does not configure Cloudflare DNS, tunnel ingress or ChatGPT connectors.

The README's V1 read-only security description applies to the original tools; this deployment adds two narrowly scoped action tools. Treat enabling `orchestration.start` on a public tunnel as a deliberate security decision.
