## Current path and evidence inventory (source inspection, not a security endorsement)

`ai-orchestration-config/scripts/orchestrate-v03.ps1` creates `.ai/tasks/<task>/audit/review-seal.json` from engine status, Git diff/status, HEAD and allowed-file hashes; `Publish-ReviewBundle` copies task evidence to `C:\work\ai-orchestration-review\reviews/<repo>__<task>[__rN]`, writes `manifest.json` (listed raw-byte file sizes/hashes) and `review-bundle.json` (manifest hash, goal/head/task), then atomically replaces `CURRENT_REVIEW.json`. The worker writes `rpc-jobs/review-<uuid>/result.json` with structural/semantic verdicts and session metadata (`model`, `provider`, reviewer profile/hash, IDs); its raw-byte SHA-256 is `evidence_sha256`. The worker reads `CURRENT_REVIEW.json` before/after review and checks bundle again. This is a useful local consistency check, not an independent principal boundary.

Read-only local ACL inspection on 2026-09-27 confirmed `workspace: FullControl` on runtime root, `reviews`, `rpc-jobs`, `rpc-jobs/authoritative`, `CURRENT_REVIEW.json`, worker source and reviewer facade. Directory rights permit creation, replacement and deletion; file owner labels do not override the effective grant. The Gateway S4U principal is `workspace`; the temporary Review Bridge and semantic OpenCode process are started by that principal. Individual historical result-file ACLs were **not** exhaustively checked; parent rights and executable writability suffice to fail the complete-compromise threat model. There is no protected monotonic generation or independent Review signing key. `review-seal.json`, SHA-256, fresh session metadata and `wx` alone cannot stop a same-principal attacker from fabricating a PASS, changing the selected bundle or replaying an old result. `CompleteReview` currently uses the local current pointer, bundle/seal and local status/boolean; it does not consult a protected Review Authority.

## Proposed authority and placement

**Recommended first design:** put the *Review Authority's publisher, semantic-review execution credentials/runtime, immutable content store, generation DB and authenticated currentness API* in a dedicated Review component inside proposed CT122, under a service principal separate from the Finalizer frontend and CT121 Signer. Use separately owned code/config/dependencies and a protected **single transaction coordinator** for generation + completion writes, no AI-controlled mount/ssh/service restart/restore rights. With SQLite there are **no table-level OS ACLs**: do not grant separate service users write access to the same DB file and call that separation. Give the coordinator exclusive file-write ownership; authenticated, narrowly scoped local socket requests from protected Review/Finalizer principals perform the publication or finalize transaction in its code. This makes the commit-time currentness check enforceable in one local serializable transaction and avoids cross-service stale-lease races. Coordinator code/config/socket permissions and request authorization are part of the trust boundary, not a generic SQL executor. The same CT122 host/root remains a shared blast radius: separate Unix users alone do **not** protect against CT root/host root or an admin who controls both. The semantic reviewer must actually run under the protected Review identity (or deliver an independently authenticated verdict); moving only the JSON pointer to CT122 leaves AI able to forge model/session metadata. Review can consume *untrusted* candidate execution evidence; independent provenance, access to the exact frozen bytes and policy-validated semantic verdict must be demonstrated before a PASS can be published. No claim that an LLM's semantic judgment is infallible.

Alternative 1, moving the present Windows Review service to a separately ACL-protected principal/storage, is only acceptable after proving AI `workspace` has no elevation, parent/loader/agent/credential access, task/service-control or restore ability; current enabled Administrators group and writable code make that a migration, not a flag change. Alternative 3, CT123, improves independence from a CT122 compromise and may allow separate operators but adds tailnet, credentials, backups, monitoring and a hard distributed currentness race. With CT123, require a protected Review-issued *fencing lease* that blocks new generations through the Finalizer commit, or equivalent coordinated transaction/consensus; a one-shot GET or signed snapshot is not enough. When CT122 itself is compromised, neither co-location nor pinned network identity saves completion; choose CT123 if the human threat model extends to CT122 root compromise. Both layouts inherit PVE host/cluster root trust and require AI-negative PVE/RBAC/backup tests before deployment.

## Record, submission and generation protocol

Protected **versioned strict record** (unknown version/status/field rejected): `schema_version`, `authority_id`, `repo_id`, `review_id` (globally never reused), `task_id`, `run_id`, `generation` (positive integer, monotonic **per `(repo_id, task_id)`**), `bundle_manifest_sha256`, `review_bundle_root_sha256` (domain-separated canonical path/size/digest tree over exact archived bytes, not a mutable filename), `canonical_goal_sha256`, `review_seal_sha256`, `structural_result`, `semantic_result`, `final_review_result` (PASS/NEEDS_WORK only), `review_evidence_hash` (raw-byte semantic/structural result artifact or explicit immutable composite root), `created_at`, `finalized_at`, `supersedes_review_id` (null only first generation), `reviewer_version`, `policy_version`, `model_session_id`, `execution_session_id`, `proposal_artifact_sha256`, `attempt_id`, `attempt_history_hash`, `failure_fingerprint` (nullable with explicit reason), `previous_record_hash`, `record_hash`. All hashes are lowercase SHA-256 with specified canonical encoding/domain separators; identify both repo and run to prevent cross-task collisions. Bind a human-display payload hash and immutable goal/Review summary to the same record; unknown policy versions or non-verifiable session evidence fail closed. Historical attempts, including failed ones, have unique IDs and immutable hashes; resubmitting an identical previously failed artifact without new trusted inputs is rejected, not presented as a fresh review. Failures and attempts are audit events, not PASS records; a new legitimate review after a failure requires a new attempt ID, changed evidence/fingerprint or explicit human-reviewed retry decision. Define precise canonical bytes and failure fingerprint inputs in implementation review.

Execution/OpenCode may submit a **candidate** with sealed bundle bytes, task/run/head, proposal artifact hash, attempted review output and previous attempt identity. Review Authority must not accept an AI-supplied PASS, `latest=true`, session ID or policy name as provenance. It copies and verifies full raw bytes/manifest/seal and trusted task/run binding; checks source snapshot freshness using independently frozen content/commit attestation (AI-editable Git HEAD/working tree alone cannot prove it); runs deterministic structural checks on protected code and a *fresh independent semantic session* on the pinned packet using Review-controlled agent/profile/credentials; verifies actual session/message provenance and exact schema/refs/policy/behavior; recomputes result hash. A compromised requester may submit a malicious candidate but may not publish, supersede or forge Review output. If credible independent semantic execution or source freshness is unavailable, **no authoritative PASS**.

Evidence hierarchy for deciding a *verdict*: protected copies of exact sealed bundle bytes/root hash → Review Authority's deterministic structural recomputation → authenticated fresh semantic session artifact bound to those bytes → protected generation/finalization record. The generation record determines **which** evaluated verdict is current; it does not turn bad evidence into good evidence. Review-agent self-report, AI summary and Dashboard/Gateway pointer are lower-trust candidate/projection, never proof of either verdict or latest state. A hash of AI-controlled material proves only byte consistency, not truthful execution or semantic correctness.

Proposed storage A: CT122-owned SQLite with `review_records` immutable after finalization, unique IDs and `(repo_id,task_id,generation)`; protected content-addressed bundle/result archive; append-only audit event chain with previous hash; `current_generation` one row per task. In one `BEGIN IMMEDIATE` transaction validate current generation and prior record, append immutable review row and audit event, update latest generation, `COMMIT`. Every new finalized PASS **or** NEEDS_WORK advances generation; a later NEEDS_WORK invalidates older PASS for LIVE. Superseding/invalidation must be recorded even if a later review fails to produce a verdict: define a protected INVALIDATED event/generation or freeze LIVE until the failure is resolved, never silently leave a once-current PASS valid after its subject changed. Journal B (append-only log + derived index) simplifies audit export but torn writes/replay/index recovery and coordinated Finalizer checks are harder. File name, mtime, AI-writable Git commit and a mutable latest pointer are not generation proof. SQL constraints/triggers and service rights must prevent UPDATE/DELETE of finalized rows; CT122 root still requires independent recovery oversight. Chain detects inconsistency but **cannot detect a rollback of the whole DB plus chain** without an independently anchored high-watermark.

For per-task `(repo_id,task_id)` latest generation `g`, LIVE requires exact `review_id`, `run_id`, `record_hash`, PASS for structural/semantic/final, all signed-approval bundle/evidence/goal hashes equal the record, and `g == record.generation` with no invalidation/supersession. A valid signature on generation 1 PASS remains a historic fact after generation 2 NEEDS_WORK or generation 3 PASS, never LIVE authority. Review record itself is immutable; latest state is separately mutable only by protected Review Authority. Do not infer latest by a caller boolean or `CURRENT_REVIEW.json`. A review generation change after CT121 signs requires **new human approval** bound to the new Review ID/hash. Retain old records for historical audit only.

## Finalizer query, signer display and authentication

Prefer **Finalizer→Review Authority direct authenticated query** by `(repo_id,task_id,run_id)` with response `{schema_version,authority_id,review_record,current_generation,current_record_hash,current_state,query_epoch}`; strict record schema and hash are verified. Same-CT122 deployment uses a protected local socket with peer credentials and separate Unix identities; the protected coordinator serializes the latest-generation check and completion commit. Different hosts require mTLS with human-pinned CA/server identity **and client identity**, tailnet ACL as additional routing restriction, no TLS verification bypass, plus the fencing/commit protocol above. DNS or AI relay must not select trusted endpoint/key; Finalizer never trusts AI-provided response JSON or a stale cached result. Tailnet HTTPS/grants alone are access controls, not authenticated review provenance; do not rely on a bearer credential readable by AI.

**Record signing decision: defer / not required for initial co-located LIVE design.** A dedicated Review Authority signature (never CT121's signer key) improves exported audit and offline verification and makes untrusted relays feasible, but introduces another private-key lifecycle and cannot establish *latest* generation from an old signed PASS. The protected direct authenticated query + coordinated generation transaction is simpler for LIVE. If CT123 or offline audit requires signatures, add a separately human-admin-managed Review signing key/ID, pinned verification key, versioned canonical record signature and independently authenticated monotonic high-watermark/currentness; a signed old record alone cannot authorize LIVE. This is a design decision, not a generated key.

CT121's approval screen must fetch or validate an authenticated **authority-owned display package** (goal text/hash, meaningful review summary, PASS, repo/task/run, review ID/generation, manifest/root/evidence hashes and display hash) rather than render only AI-provided prose or Dashboard projection. Pin Review Authority identity at the Approver UI or obtain a Finalizer-authenticated package with verifiable original Review source; do not expose admin/mutation credentials to CT121. Human UV signs the exact existing v1 evidence bindings; v1 has no generation/display hash in its signed payload, so Finalizer must compare immutable review ID/hashes plus independently confirmed latest generation. For a stronger explicit display-to-signature binding, approve a **versioned v2** payload including generation/display hash before production; never silently add fields to strict v1. The human should be shown the hashes/goal and stale/mismatch means no issuance. A signed A cannot finalize B.

## Recovery, tests and legacy disposition

CT122 Review+Finalizer transaction DB, protected content archive and audit must have a consistent AI-inaccessible recovery plan; record high-watermark/generation roots must be anchored **outside rollback scope** (e.g., human-admin offline receipt plus separately protected monotonic store, with reconciled Finalizer checkpoint). A human receipt only taken occasionally cannot detect rollback beyond its last checkpoint; until a durable per-commit anchor/fencing design is chosen, restore is **fail closed** with human comparison/reconciliation, not automatic activation. On DB corruption, missing newest record, chain gap, lost key/identity, uncertain attempt history or unavailable authority: stop new Review publication and Finalization, do not recreate generation 1, recover only by human-admin verified history and new epoch/domain if continuity cannot be proved. Backups/restore rights remain inaccessible to AI; retention/availability of old records supports historical audit.

Negative E2E under compromised AI principal: unknown Review ID; wrong repo/task/run; wrong manifest, bundle root, seal, goal or result raw-byte hash; missing structural or semantic artifact; malformed/unknown policy, model-session mismatch; forged PASS JSON or code/profile; modified/deleted newest record; stale/superseded PASS; revert after NEEDS_WORK; whole-store rollback and restored stale backup; same failed artifact with new label; change `CURRENT_REVIEW.json` or Gateway/Dashboard PASS; tampered relay/fake endpoint/DNS and invalid mTLS identity; Review outage; Review superseded between approval and Finalizer commit; direct Complete fallback. **All must reject LIVE DONE**, retain historical evidence, and leave Finalizer JTI/completion unchanged. Exercise concurrent Review publication vs Finalizer commit and crash/restore boundaries, with actual AI token/PVE negative rights, not just mocks. Existing local tests do not prove these properties; no prototype or production tests were run for this document.

Canonical source-of-truth split: execution engine evidence = *untrusted execution candidate*; protected Review Authority = Review truth/current generation; CT121 = human UV/signing truth; CT122 Finalizer = authoritative DONE; `.ai`, `CURRENT_REVIEW.json`, Dashboard/Gateway = projections/navigation only. No production migration, service restart, key generation, ACL or CT change is authorized here.
