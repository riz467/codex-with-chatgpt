# Unattended recovery after VM reboot (Server 2022)

**Prepared, not activated.** Do not reboot, enable autologon or change the production Gateway without a separate human approval. Gateway, Review Bridge and cloudflared remain on the existing S4U startup task. Only Codex worker uses the workspace InteractiveToken logon task. No arbitrary command entry point, approval change, sandbox change or automatic task-attempt retry is added.

## Choice and risk

| Method | Credential storage / viability |
| --- | --- |
| Winlogon AutoAdminLogon configured directly through Registry Editor | `DefaultPassword` is **plaintext in the registry** (Microsoft warns Authenticated Users can remotely read the key). Do not use. |
| **Microsoft Sysinternals Autologon GUI (chosen)** | Configures built-in Winlogon automatic **console** logon; password stored as an encrypted **LSA secret**, not plaintext `DefaultPassword`. A local administrator can still retrieve/decrypt it. Supports the Windows Server automatic logon mechanism; password must be entered by a human in its GUI, never CLI arguments, script, repository, transcript or config file. Does not validate credentials at setup time. |
| Scheduled Task AtStartup, S4U or service without a desktop | Does not create the required InteractiveToken session; observed runner `0xc0000142` in Session 0. Not a substitute for console logon. |
| Restart sign-on / automatic restart sign-on (ARSO) | Intended for completing updates using the last interactive user, not a guaranteed unattended logon after an arbitrary cold reboot. Not selected. |

Official references: [Sysinternals Autologon](https://learn.microsoft.com/en-us/sysinternals/downloads/autologon), [Windows Server automatic logon](https://learn.microsoft.com/en-us/troubleshoot/windows-server/user-profiles-and-logon/turn-on-automatic-logon). The latter documents plaintext-registry risk, logon-banner/EAS restrictions and a possible `DefaultUserName` change after another user's interactive console logon. Console access to an already authenticated admin account is a serious risk: secure the VM console/hypervisor, disk and backups, restrict administrator rights and remote registry access, and lock the desktop after boot without signing off. Autologon is **not** equivalent to a locked session. RDP reconnect/disconnect should preserve the session; **sign out/log off terminates it**, and a new logon may create a different session. Do not promise reliability until the actual reboot test.

## One-time human setup (elevated workspace interactive session)

1. Review the ACLs on the worker queue, binaries and logs (workspace and Administrators only), the installed worker task (`Get-ScheduledTask AI-Workspace-Codex-InteractiveWorker | Format-List *`), its fixed action, its workspace principal and its AtLogOn trigger. It must be `Interactive` (Task Scheduler UI: **Run only when user is logged on**), `Highest`, `IgnoreNew`, unlimited execution limit, restart on failure (3 times, 1-minute interval). `scripts/install-codex-interactive-worker.ps1` registers only when absent; the explicit `-Update` path is reserved for a stopped, version-matched legacy action and requires a separately approved change procedure. The normal action is `wscript.exe` with the fixed VBS launcher, which invokes hidden PowerShell with the fixed worker entrypoint; the old direct `pwsh.exe` task action is not reboot-ready. The worker also validates workspace SID, Interactive group and SessionId > 0, and refuses S4U/batch tokens. Its lock and durable claim prevent parallel execution or automatic replay of an uncertain attempt.
2. From the [Microsoft Sysinternals download](https://learn.microsoft.com/en-us/sysinternals/downloads/autologon), obtain and verify the signed binary through the normal administrator process. Run its GUI **locally in the elevated admin session** (do not pass username/domain/password on the command line). Enter `workspace`, the VM's local computer name (not an AD domain unless the account really is domain-joined), and the password **in the GUI only**; click Enable. Do not record the password in PowerShell history, a transcript, screenshots, tickets or Git. Check GUI Enabled. Reject setup if `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\DefaultPassword` exists; never dump an LSA secret. Do not use a one-time autologon count (`AutoLogonCount`) for ongoing unattended recovery.
3. Run `pwsh -NoProfile -File scripts/status-ai-workspace-gateway.ps1` and `pwsh -NoProfile -File scripts/preflight-ai-workspace-autologon.ps1`. The latter **reads no password**, checks only non-secret Winlogon values, task configuration, live Interactive worker heartbeat and S4U Gateway/Review health. Verify cloudflared status and external health in the status output, and verify the current production Gateway still uses S4U. Confirm the Autologon GUI setting manually: preflight cannot prove the LSA secret is present or valid. Keep the rollback below available to the operator before approving reboot.
4. Check that no interactive-logon legal notice or Exchange ActiveSync password policy blocks autologon. If another account logs on at the console, recheck `DefaultUserName` before the next reboot; do **not** add a shutdown script that writes credentials. Account/password rotation requires repeating the GUI step. Do not disable security policies merely to make autologon pass without a security review.

## Reboot test — requires explicit human authorization

Do **not** initiate this test from automation. Before reboot, record the health/heartbeat and preflight result, task principal/trigger/action and rollback readiness. After reboot, observe from the **ChatGPT/Gateway side or console management without RDP login**: S4U Gateway/Review/cloudflared started, workspace console interactive session exists with SessionId > 0, logon-state `Active` or `Disconnected`, worker task running with matching PID/SessionId and continuously updating heartbeat, worker ready for Codex execution. Confirm that these timestamps predate the first human RDP connection. Then submit an approved **read-only orchestration** using the existing production approval/sandbox boundary; require success, no runner pipe timeout and no `0xc0000142`. A heartbeat alone does not prove the runner works. Never replay a reserved attempt blindly. A failed check means **NO** to unattended readiness.

## Rollback / incident response

From a human elevated admin console, open the same trusted Sysinternals Autologon GUI and click **Disable**; confirm `AutoAdminLogon` is off and there is no plaintext `DefaultPassword`. Do not export or print the LSA secret. If the worker must be stopped, first investigate running/reserved requests (unknown outcomes are not automatically retried); then disable `AI-Workspace-Codex-InteractiveWorker` using Task Scheduler, without changing Gateway/Review/cloudflared. Do not log off/restart while a request is active without an explicit incident decision. Re-enable only after the root cause is reviewed. If access is lost, use an authorized hypervisor console/admin recovery procedure; do not store an emergency password in this repository.
