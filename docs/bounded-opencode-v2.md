# Bounded OpenCode v2 — fixture-only target, operating Execution Bridge runtime

## Scope and non-goals

The bounded v2 MCP tools are available in the operating Execution Bridge, but their repository allowlist contains only `autonomous-fixture` (`C:\work\bounded-review-live-fixture`), **not** `pve-doc`. The contract fixes `task_kind=text_change`, `execution_profile=tracked_utf8_text`, `worker=opencode`, and `codex.allowed=false/max_calls=0`. It permits 1–3 existing tracked UTF-8 text files, not arbitrary shell commands, tests, profiles, or production operations. The fixed verification checks the tracked diff and permitted paths; a code-test profile would need separately designed isolation. Neither the worker nor any subsequent review or Passkey step commits, pushes, deploys, or completes legacy `DONE`.

## Bounded task lifecycle and durable evidence

`start_bounded_opencode_task` (`orchestration.start`) stores a canonical contract and SHA-256, clean-repository baseline HEAD and scoped file hashes, and reserves the repository. A dedicated read-only OpenCode proposer receives the bounded file contents and returns exact text replacements; the controller validates scope, UTF-8, unique old text, unchanged snapshots, and the resulting diff before moving `RUNNING` to `REVIEW_PENDING`. It preserves revision-indexed input, proposal, diff, verification and worker evidence. Verification failure escalates rather than silently retrying. No Codex call or fabricated Codex usage is attributed to this worker.

`get_bounded_task`, `list_bounded_artifacts`, and paged-base64 `read_bounded_artifact` require `review.read`. Artifacts are checked against their manifest SHA-256, per-file size and byte hashes. `submit_bounded_chatgpt_review` delegates task ID, latest revision, contract hash, manifest hash, stored evidence and live Git diff checks to the ledger. An identical review delivery is idempotent; stale, cross-task, mismatched, or changed evidence is rejected. `PASS` produces `REVIEW_ACCEPTED`, **not** `DONE`; `NEEDS_WORK` returns to `RUNNING` for a new revision within the same bounded scope, at most three revisions by default. Exhaustion or failure gives `ESCALATE`. Review waiting does not consume worker time; the repository reservation spans the wait. Crash-during-execution leaves a lock for manual inspection, not an automatic replay.

The default ledger root is `%LOCALAPPDATA%\codex-with-chatgpt\bounded-v2` on Windows (`tasks/` and `repo-locks/`); `C2C_STATE_DIR` selects the state root instead. Controller restart can re-read the contract, revisions and pending review without depending on `TEMP`. Historical task evidence is not rewritten during migration or restart. Contract hash, artifact manifest/files, saved review record and accepted live diff are rechecked before an accepted snapshot is used. This is local consistency checking, **not** an independently protected signature against compromise of the same OS principal.

## OpenCode worker and authenticated ChatGPT review return

The worker adapter uses the dedicated `c2c-bounded-proposer` agent and the fixed local OpenCode proposal script; do not substitute the general build agent or a semantic-review agent. A dedicated fixture may carry `.opencode/agents/c2c-bounded-proposer.md`. The proposer has no tool permissions and is not the independent ChatGPT reviewer. The real-worker probe in `tests/real-bounded-opencode.mts` is explicit opt-in, requires a precommitted isolated fixture seed and the external adapter/agent, and is **not** part of the automatic test suite. Provider/model/usage are recorded as observed, not invented.

Review return is connected through authenticated Execution Bridge MCP, not an OpenCode self-review. `orchestration.review` is explicitly requested at OAuth pairing: omitted or unknown scopes do not grant it, and refresh of an old token cannot add it. The consent page does not describe `orchestration.start` or `orchestration.review` as read-only. `submit_bounded_chatgpt_review` requires a bearer-derived principal with that scope **and** a client ID matching the Execution Bridge's server-owned `C2C_BOUNDED_REVIEW_CLIENT_ID` (or explicitly supplied server option). With no configured ID it denies all. A tool argument, `reviewer: "chatgpt"` label, OAuth registration name, or generic scope alone cannot establish reviewer identity. Calls without `authInfo` fail closed. The Review-bound Bridge rejects review return even if given the same client binding; only the authorized Execution Bridge client can submit it. Connection identity is an OAuth/client-configuration boundary, not proof supplied by arbitrary model text.

## Test-only Passkey binding

`BoundedTasks.acceptedSnapshot(task_id)` supplies the accepted task ID, revision, contract/manifest/diff SHA-256, summary, review ID and `PASS` result to an isolated `PasskeyFixture`. The fixture hashes the entire displayed request and binds `(request_id, request_sha256)` to a single-use WebAuthn ceremony. Status, options issuance and completion recheck the live accepted snapshot; changed task/review evidence or diff fails closed. Only explicit fixture injection in `mode=localhost` exposes fixture routes. POSTs require matching Origin, Host and JSON content type; authentication requires an already registered credential, the correct challenge, origin and RP ID, signature and user verification. The existing credential counter is updated after successful verification. The screen does not automatically register a credential; `event.isTrusted` is a UI check, **not** the security boundary.

Success writes one isolated `PASSKEY_FIXTURE_COMPLETION_ONLY` receipt with `TEST_COMPLETION_RECORDED`; the bounded task remains `REVIEW_ACCEPTED`. This does not approve production work, alter legacy `DONE`, or trigger `complete_orchestration`, `complete_integrated_orchestration`, `complete_autonomous_orchestration`, commit, push or deployment. The manual browser helper `tests/fixtures/serve-passkey-dashboard.mts` requires an explicit accepted task ID and existing local Passkey; it is not auto-run. It copies only the existing credential's public material into a temporary fixture, so counter updates do **not** change the original credential store. Its receipt MAC uses a process-local key for test-process tamper detection: an old receipt is not an approval trust anchor after restart.

## Runtime separation and legacy retry

The operating Execution Bridge listens on `127.0.0.1:48765` from `.tooling/ai-workspace-execution-runtime/dist/cli/index.js`; the Review Bridge listens on `127.0.0.1:54108` from the repository's normal `dist/cli/index.js`, bound to `C:\work\ai-orchestration-review`. Their workspaces, OAuth grants and roles remain distinct. Do not use an older temporary bounded release as the normal Execution runtime, treat a Review-workspace connection as review-return authority, or infer deployment merely from a source commit. For supervisor, promotion and health procedures, see [the gateway runbook](ai-workspace-runbook.md) and [gateway reference](ai-workspace-gateway.md).

Legacy orchestration retry is separate from bounded v2's `NEEDS_WORK` revisions. In the legacy gateway, an explicit version-1 policy `STOP_*` or a present but unverified/incomplete gate is ineligible for automatic retry, even when classified `EXECUTION_BLOCKED`; it needs a newly authorized contract. A validated `ALLOW_BOUNDED_EDIT` continues through the existing retry eligibility checks. Older tasks **without** `gate_decision` retain their historical retry behavior. Neither classification nor a caller-supplied retry reason bypasses these checks.

## Remaining limitations

Only the isolated, non-secret fixture repository is enabled. The source and preserved evidence do not provide a trust anchor against same-OS administrator compromise; production evidence may contain file contents, so redaction and stronger independent approval authority need separate design and authorization. ChatGPT review is not human Passkey approval, and Passkey is not legacy `DONE`. Running a real browser helper, opening `pve-doc`, arbitrary code tests, provider changes, and any production commit/push/deployment require separate approval; none follows from these fixture results.
