# Isolated Human Approver CT — deployment preparation

This is a **service implementation and installation artifact**, not a production approval launch. It is not connected to autonomous Complete or DONE. Do not use the existing Windows PoC credential or the existing Windows tailnet hostname as the CT RP. Choose a **stable CT tailnet HTTPS name** before enrollment. A separate PVE administrator must verify CT isolation and ACLs before use.

## Trust / topology

Debian 13 unprivileged LXC: 1 vCPU, 512 MiB RAM, 4 GiB disk. Dedicated `ai-approver` system user, no login shell, no OpenCode/Codex, no Git checkout, no AI-Workspace bind mount/shared writable filesystem/SSH private key/sudo credential. PVE host/cluster root, CT root and Tailscale control plane compromise are out of scope. No Funnel. Human browser → tailnet-only Tailscale Serve HTTPS 443 → CT `127.0.0.1:48768`. AI-Workspace → bounded request submission/evidence retrieval (separate tailnet grants/ACLs or dedicated API frontend recommended; path ACLs must not be assumed from a shared hostname). CT-local root/admin → `runuser` CLI for key initialization and one-time enrollment. Backend **never** listens on a tailnet IP.

`src/approver-service/` is deliberately independent of Gateway/Dashboard and imports only the existing `src/human-approval/contract.ts` for byte-identical v1 signing. The packaged runtime contains only those two modules and the service's dependencies, not this repository's other runtime, Git history, or dev tools. `npm ci --omit=dev --ignore-scripts` is run only on the CT against the packaged lockfile. Node.js **24+ with built-in `node:sqlite`** is required (`/usr/bin/node`). A CT root administrator installs Node 24 through their approved distribution mechanism; this repository does not install Node or reconfigure Tailscale.

## Build / install (on separate CT, not Windows)

On a build host: `pnpm approver:pack`. Transfer **only** `dist/ai-approver-package/` (or an authenticated archive of it) to the CT. Inspect its contents; do not transfer `.git`, `node_modules`, any existing credential store, or any key. As CT root, inspect the artifact and execute:

```sh
sh /path/to/ai-approver-package/install.sh /path/to/ai-approver-package ai-approver.<tailnet>.ts.net
runuser -u ai-approver -- /usr/bin/node /opt/ai-approver/runtime/approver-service/cli.js init
runuser -u ai-approver -- /usr/bin/node /opt/ai-approver/runtime/approver-service/cli.js public-key
systemctl enable --now ai-approver
tailscale serve --bg --https=443 http://127.0.0.1:48768
tailscale serve status
```

Before applying Serve, inspect `tailscale serve status --json` and do not overwrite an existing mapping. Ensure DNS/HTTPS grants expose this name only to intended tailnet clients; **never use `tailscale funnel`**. Copy the public-key PEM and key ID to a separately controlled verifier trust configuration in a future phase. Never copy `/var/lib/ai-approver/signing.key` to AI-Workspace, backups accessible by AI, or this repo. Installer does not start or enable service; it doesn't create a key. On updates, stop CT service, back up DB/key under CT administration, install reviewed artifacts, check DB migration compatibility and restart CT service only. Systemd unit uses fixed executable/cwd/config, `Restart=on-failure`, `UMask=0077`, `NoNewPrivileges`, `ProtectSystem=strict`, and only `/var/lib/ai-approver` writable. `/opt/ai-approver` and `/etc/ai-approver/config.json` are root-owned; `/var/lib/ai-approver` is `ai-approver`-owned. Installer refuses to overwrite an existing config; `init` refuses to overwrite an existing signing key. CT admin must verify owner/mode of DB, WAL, SHM and key in the real CT.

## Enrollment / API

After service starts, a CT admin executes `runuser -u ai-approver -- /usr/bin/node /opt/ai-approver/runtime/approver-service/cli.js enroll-open` **locally**. It prints a 256-bit random secret invitation URL expiring in five minutes. Deliver it directly to the human, never to AI-Workspace. The hash (not the token) is in SQLite. `GET /enroll/:token` opens enrollment UI; `POST /enrollment/options` and `/enrollment/verify` require the token and browser origin. The registration challenge expires after two minutes and is consumed **before** verification. Successful UV-required registration closes the invitation; failed/replayed/expired attempts do not add credentials. Bitwarden, Windows Hello and other FIDO2 authenticators are allowed; no attachment restriction. WebAuthn private keys, PINs and biometrics never enter the server. Credential disable/recovery is CT-local administrative work (the store exposes a disabled flag; no HTTP mutation API). An admin must control enrollment window issuance and monitor audit events.

The AI can `POST /api/approval-requests` with **only** the existing strict v1 request JSON (no paths, command or arbitrary text) and later `GET /api/approval-evidence/:requestId`. `GET /approve/:requestId` displays task ID, run ID, **claimed** Review PASS/Review ID, canonical goal **SHA-256 as a safe display, not goal text**, evidence/manifest hashes and expiry. The human presses **パスキーで承認**: browser invokes `navigator.credentials.get`; server verifies server-generated single-use challenge, fixed HTTPS origin/RP, credential signature, UV and counter, then signs the exact stored request with Ed25519. `POST /api/webauthn/authentication/options` and `/verify` only accept fixed fields and browser Origin/Host, and do not issue evidence on an HTTP POST alone. `GET /health` is non-sensitive. There are no shell, key export, enrollment-open or arbitrary file APIs. API Origin/Host are not a security boundary against a CLI client; signature/UV and CT isolation are.

**Important limitation:** the Approver CT has no independent authenticated Review/goal feed yet. It shows a digest and marks Review PASS as a *requester claim*, not a verified fact. Humans cannot assess goal semantics from a digest. The existing AI-side verifier requires an independently established current Review snapshot, but no production adapter provides it yet. Before production human approval, add a trusted human-readable goal/review presentation from a protected source and a currentness check at the issuer/consumer boundary. An attacker who can persuade a human to approve a misleading request is not solved by Ed25519 alone.

## SQLite / cryptography

SQLite WAL, foreign keys and busy timeout; no collection of JSON files. `webauthn_credentials`: ID, COSE public key, sign count, transports, created, enabled. `approval_requests`: ID, canonical payload, unique nonce/jti, challenge + ceremony + expiry, issued/expiry, state. `approval_evidence`: one signed v1 envelope per request, unique jti, approved time. `consumed_jti`: unique jti and consumption time (**reserved for a future Complete gate; not consumed by signing**). `audit`: timestamp, bounded event/result/request ID and safe metadata (no assertions, secret tokens or PIN). `enrollment_window` and `enrollment_challenges`: hashed one-use invitation and expiring single-use challenge. Transactions bind counter update, approval state, evidence and audit. Ephemeral test keys are generated in tests; the production key is generated **only inside the CT** by `init`, mode `0600`, under service user; startup refuses unsafe ownership/permissions. Only the public key ID/PEM will eventually reside at AI-Workspace. Back up and rotate key under independent CT administration.

## Remaining deployment checks / no-DONE condition

Tested with a software WebAuthn authenticator and temporary SQLite/key: valid registration and signed issuance pass the existing `verifySignedApproval` unchanged; unsigned/wrong-key/tampered/binding/time/replay, no-UV, challenge replay, disabled credential, bad counter and closed/expired enrollment fail. **Not** a substitute for a real CT test: verify actual tailnet DNS/TLS/ACL, Bitwarden/Hello UI and UV, systemd sandbox, DB/key ACL against AI-Workspace, bootstrap/recovery, backups, installer behavior on Debian 13 and signing public-key pinning. Also review whether the display/authorization UX sufficiently explains the real task/goal. No production approval or DONE/Complete integration is permitted by this artifact.
