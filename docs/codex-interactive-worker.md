# InteractiveToken Codex transport (staged, not enabled)

This is a transport for the existing `orchestrate-v03.ps1` `Run-Codex` invocation, not another task engine. Gateway, Review Bridge and cloudflared stay S4U. The engine keeps the task ledger, schema, prompt, approval, audit, proposal parsing, verification and review publication. No commit or push path is introduced.

## Boundary

- Queue: `C:\work\ai-workspace-logs\codex-worker\{requests,claims,results}`. Restrict the directory to the trusted workspace account and Administrators; never allow untrusted users to modify the engine's task files, worker binaries or queue. SHA-256 and nonce are correlation/integrity checks, **not authentication against another process running as workspace**.
- Request has only `task_id`, allowlisted `repo`, `attempt` (1 or 2), `kind`, nonce, prompt SHA-256 and request hash. The worker reloads the engine's `status.json`, `.prompt.txt` and `.argv.json`; it compares the argv with the fixed `-a never -C <repo> exec -s read-only --output-schema <schema> -` form. It launches only the pinned Node/Codex CLI from the allowlisted repo, without a shell. Diagnostic mode uses one built-in read-only prompt and `--ephemeral`.
- A durable per-attempt reservation refuses duplicate requests. A `.running` marker stops automatic re-execution after a crash. An unknown outcome must be investigated; do not automatically retry the same attempt. Result requires matching task ID, attempt, nonce and request hash. Before submission the client requires a live interactive heartbeat (PID, SessionId > 0, under 10 seconds). Missing worker fails closed. A request already submitted may remain reserved if the worker dies; timeout is an error, not a signal to repeat execution.
- `stdout`, `stderr`, exit code and SessionId are returned in the result. Logs can contain repository data: keep queue ACLs private. The worker is not a generic execution service. An administrator must still validate the actual Scheduled Task action/principal and writable paths.

## Install and diagnostic (elevated workspace Interactive PowerShell required)

1. `pnpm build` and `pnpm test`. Review paths/ACLs and ensure `C:\work\pve-doc\AGENTS.md` and `03_services\ai-workspace.md` exist.
2. `pwsh -NoProfile -File scripts/install-codex-interactive-worker.ps1` registers a separate `AI-Workspace-Codex-InteractiveWorker`: AtLogOn workspace, InteractiveToken (`Interactive` in PowerShell), Highest, IgnoreNew, unlimited execution time, restart 3 times at one-minute intervals. An existing task can be migrated with `-Update` only when its old action and principal match the pinned configuration and it is stopped. The task uses `wscript.exe //B //Nologo` with a fixed VBScript launcher, which waits for the hidden PowerShell entrypoint to exit and forwards its exit code. The PowerShell entrypoint retains workspace SID, interactive token, non-Batch and SessionId > 0 checks before starting the pinned Node worker. No user-visible worker console is required. It does **not** change the Gateway task.
3. `Start-ScheduledTask -TaskName AI-Workspace-Codex-InteractiveWorker`; use `pwsh -File scripts/status-ai-workspace-gateway.ps1` to check PID, SessionId > 0, logon `Interactive` and heartbeat. A missing or expired heartbeat is not ready; the last Task Scheduler result is only historical and does not by itself override a verified live worker.
4. From an interactive workspace shell start a **single** fixed diagnostic, using a unique ID for that one run: `& 'C:\Users\workspace\AppData\Local\Author Software\nvm\installs\v24.16.0\node.exe' 'C:\work\codex-with-chatgpt\dist\worker\cli.js' diagnostic 'C:\work\pve-doc' diag-rdp-001 1`. Save its JSON result. The built-in prompt runs `pwd`, `git status --short`, reads `AGENTS.md` and the first 40 lines of `03_services/ai-workspace.md`; inspect stdout/stderr, exit code and runner errors. For a long-running test, enqueue immediately before disconnecting, then disconnect RDP **without logging off**. Wait 5–10 minutes and reconnect; compare PID and SessionId against the initial heartbeat, task state, result and timestamps. Confirm no runner pipe timeout or `0xc0000142` in stderr and that all four reads succeeded. Do not count mere process survival as a successful Codex run.
5. No VM reboot is authorized until this disconnected-session test succeeds. InteractiveToken starts on **logon**, not at startup: VM reboot recovery requires a separately reviewed auto-logon/session strategy, and is intentionally not implemented here.

## Engine integration (deferred until diagnostic passes)

`scripts/enable-codex-interactive-engine-hook.ps1` without `-Apply` is a preview. After successful RDP test, run with `-Apply` only after reviewing the version-guarded insertion and its backup of the external engine `C:\Users\workspace\.config\opencode\scripts\orchestrate-v03.ps1`. The branch delegates after the engine writes prompt and argv, and returns stdout/stderr/exit to the original engine flow. It is **opt-in** via `AI_CODEX_WORKER_ENABLED=1` on the Gateway process, followed by a separately authorized Gateway restart. Before then, direct Codex remains the production path; do not use the hook's opt-in flag on a production Gateway until a bounded end-to-end engine test passes. No changes to approval gate, ledger, bundle or state machine are required.

If the worker stops while executing, the adapter times out and the engine follows its existing error handling. Inspect the reserved task/attempt before any new run. Never clear claims or results to force a retry.
