# Autonomous Review framework — structural and semantic phases

`scripts/autonomous-review-worker.ts` is a **Review-side** structural worker. The execution controller can invoke it only with a fixed allowlist repo key, `rpc-<32 hex>` task ID, and baseline HEAD; it does not accept arbitrary paths, shell commands, bundle directories, profile names or a review result. It starts a temporary loopback Review-bound MCP Bridge with a one-use local auth store, uses `workspace_info` and `read_file` to inspect `CURRENT_REVIEW.json`, the published bundle and autonomous decision records, and calls the existing `verify_bundle_integrity` MCP tool for raw-byte validation. It never calls an Execution Bridge completion tool. The permanent VM Bridge/ChatGPT connector is not reconfigured or replaced.

Common checks live in `src/mcp/review-structural.ts`: status, successful Verify, baseline, seal/diff hashes against the raw-byte manifest, fixed edit scope, Git status, task audit and autonomous Decisions. `src/mcp/review-profiles.ts` is the trusted Review-only repo/profile allowlist. The old document-policy check is isolated under `src/mcp/review-profiles/fixture-document-policy.ts` and runs **only** for that fixture profile. Generic text requires structural evidence; generic code additionally requires a sealed `audit/autonomous-tests.json` PASS record bound to the edited path and byte hash. For the PowerShell fixture this is a parse-only syntax test, not a behavioural test. An extra required-file profile exercises `EVIDENCE_MISSING`; timeout uses the isolated `tests/fixtures/review-timeout.mjs` transport shim, not a fake Review verdict. Structural PASS alone is never a new final PASS.

The worker writes one bounded result to `C:\work\ai-orchestration-review\rpc-jobs\review-<uuid>\result.json`, outside the immutable bundle, and returns it with its byte hash. `PASS` never authorizes completion. A moved `CURRENT_REVIEW.json` pointer, unavailable MCP or malformed result is an error, not PASS. The execution controller never scores Review evidence and uses no transport retry when the result is uncertain.

## Semantic phase (opt-in per trusted Review profile)

Legacy profiles without an enabled semantic policy now fail closed as NEEDS_WORK (`SEMANTIC_REVIEW_INTERNAL_ERROR`) after structural PASS. Historical structural-only results remain readable as historical evidence, not approval candidates; enabling a new repo requires a trusted semantic profile.

After raw-byte integrity and `STRUCTURAL_REVIEW = PASS`, the worker constructs a capped, numbered evidence packet exclusively from the sealed bundle: goal, fixed scope/baseline, research, plan, decisions, bounded diff, verification and test summary. It starts a separate, password-protected loopback OpenCode V2 server bound to the Review workspace, creates a **new** `c2c-semantic-reviewer` session, and does not pass the execution session history, prompts, reasoning or runtime paths. This agent has no tools; a single answer must match `review_result`, `reason_category`, `summary`, `evidence_refs`, `unresolved_issues` exactly. A malformed answer, unavailable server or timeout escalates; it cannot become PASS. The worker records reviewer session ID, profile hash, model, provider, usage and manifest hash in Review-owned evidence; execution only validates the result hash and envelope. Review usage is separate from execution OpenCode usage.

The sealed original goal is the canonical requirement. The bundle metadata and current pointer bind its SHA-256 to the sealed status and execution run. A Review profile only supplies scope, risk/behavioral-test policy and required evidence, never a target value. For an unambiguous numeric timeout change in the original goal, the sealed behavioral observation must match the requested target even when the model claims PASS. Ambiguous goals fail closed. A parse-only test cannot support a behavioral PASS. Other code domains require their own relevant trustworthy behavioral tests and policy. A historical experimental job (`review-b1afa4c5-7b70-4e3b-b38d-542b7efbc750`) incorrectly passed a contradictory goal; **it cannot be approved** and remains intact as audit evidence.

## Human approval gate and autonomous MCP entry

`src/mcp/autonomous-approval.ts` requires `{ task_id, review_result: "PASS", review_evidence_hash, bundle_manifest_sha256, authoritative_review_id, done_approved: true }`. It checks the current per-task authoritative pointer, exact Review-owned result bytes, both phase verdicts, raw-byte bundle integrity and canonical goal across live ledger, immutable bundle and execution run. It rejects old results and free-form approval. Its MCP completion method additionally requires an exact current `rpc-jobs/human-approvals/<task>/current.json` record bound to the run, goal, Review and bundle, matches it against append-only audit, and atomically marks its nonce consumed before invoking the existing engine `CompleteReview` or `CompleteIntegratedReview`. The gateway's legacy completion endpoints refuse registered autonomous tasks. A caller boolean alone is insufficient. An interrupted completion after consumption requires investigation rather than silent retry.

**Production provenance blocker:** The new Dashboard button, one-time in-memory CSRF, Origin/Fetch-Metadata checks, loopback restriction and `event.isTrusted` defend against accidental/remote browser requests, **not** against an agent with same-user local HTTP/filesystem access. Such an agent can GET `/approval/current`, obtain cookie/CSRF, POST `/approval/final`, or write the evidence files itself. The synthetic fixture E2E does exactly the first sequence and is *not* proof of human origin. The production Dashboard entrypoint therefore keeps approval routes disabled (`APPROVAL_NOT_CONFIGURED`); only explicitly created isolated fixture instances enable them. Do not claim human-origin enforcement or turn this on in production until the Dashboard approval issuer and evidence store run behind an independently verified OS principal/ACL or equivalently separate trusted human authentication channel that the ChatGPT/OpenCode/Codex principals cannot access, with tests for direct HTTP and filesystem forgery. No such credentials/ACL boundary are provisioned in this campaign. The MCP tool remains fail-closed without a valid evidence record but cannot authenticate the record's origin when the caller can write its files.

`start_orchestration(mode="autonomous")` accepts a trusted repo key, goal and optional scope that must equal the profile's single fixed edit path. OpenCode holds the run's research, plan and Verify decisions; Codex is bounded to one implementation. The existing status/result tools expose run/task IDs, phase, actor, Review, human action and usage. The local Bridge fixture completed one-shot goal → Review PASS → fixed fixture approval → existing CompleteReview → DONE without restarting the production connector. The dashboard projects these run records and events read-only over its existing SSE snapshot; its health verification retains unknown/degraded for inaccessible Windows evidence.

The Review workspace allowlist in `src/mcp/review-profiles.ts` is separate from the legacy `REPOS` map for `read_only`/`change`. Autonomous fixture changes require both an execution profile and a trusted Review profile. Publishing a newer bundle moves `CURRENT_REVIEW.json`, invalidating a prior approval. PASS alone ends at `HUMAN_FINAL_APPROVAL`; production human approval must still be provided through a trusted explicit channel, not inferred from text or a model's own boolean. Commit and push are not part of this route.

## Production activation checklist (not executed)

1. Provision and independently test the human-only OS/auth principal and protected evidence store. Deny the OpenCode, Codex and ChatGPT Bridge principals both approval-issuer HTTP access and direct write access to the approval audit/current/consumption directory. Replace the fixture-only Dashboard opt-in with an authenticated production issuer; test same-user HTTP/filesystem forgery, replay, stale pointer, bundle/goal/scope mismatch and crash recovery. Without this step approval stays disabled and activation is **NO**.
2. Resolve the shared `CURRENT_REVIEW.json` before use: it can point to an isolated fixture. Do not guess or restore an old value. Have the operator identify the intended production task and publish/select its authoritative Review under the normal engine flow. Confirm task ID, workspace, goal hash and Review result match; no historical fixture result authorizes a production task.
3. Review the two repositories' uncommitted diffs and existing user edits before authorizing commits or rollout. Run both full test suites, typecheck/build, `git diff --check`, then the official `deploy/sync-opencode-config.ps1` DryRun → Deploy → Check and runtime engine `-SelfCheck`. This campaign updated managed OpenCode files without starting any production service.
4. With explicit operator approval and a maintenance window, deploy the built Bridge/Dashboard/Review worker code. Restart the **production Gateway/Bridge** to load new MCP schemas/tools and worker code; restart the **Dashboard** to load the new UI/server/build. Refresh/rescan the ChatGPT connector tools after the Bridge restart and verify their schemas/scopes. Review scheduled-task definitions only if launch paths/options change; do not recreate them merely to load code. Review worker launched per review uses updated code on its next isolated launch. Confirm health and a new production Review before accepting an approval.
5. No production Gateway/Dashboard/Scheduled Task restart, task registration, commit or push occurred in this campaign. Fixture PASS/DONE is not a production acceptance signal.
